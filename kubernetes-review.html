What problem does Kubernetes solve that Docker alone doesn’t?

Docker answers “how do I run this app anywhere?” Kubernetes answers “how do I keep hundreds of these running, reachable, and healthy across a fleet of machines, without a human watching?” Everything below is built from that one question.

01

Why Kubernetes if we already have Docker?

Docker and Kubernetes are not competitors and they do not overlap much. Docker is a packaging and runtime tool. Kubernetes is an orchestrator. One builds and starts the box; the other decides how many boxes, on which machines, and what happens when a machine dies.

What Docker solves

Before containers, “works on my machine” was a real class of production bug. Docker fixed a specific and important set of problems:

Packaging

An image bundles the app, its runtime, libraries, and filesystem into one immutable, versioned artifact. The same bytes run on a laptop and in production.

Isolation

Namespaces and cgroups give each process its own view of PIDs, network, and mounts, with limits on CPU and memory — without the cost of a full VM.

Portability & distribution

Registries make an image pullable anywhere. docker push / docker pull replaced hand-built servers and config drift.

Fast, repeatable startup

Seconds to boot instead of minutes, because there is no guest OS — containers share the host kernel. This is what makes elastic scaling even thinkable.

What Docker does not solve

Every item below is something you would otherwise have to build yourself with scripts, cron, a load balancer, and a person on call.

Scheduling across machines

Docker runs containers on the host you typed the command on. It has no idea which of your 40 servers has spare memory.

Self-healing

--restart=always restarts a crashed container on the same host. If the host dies, nothing moves the workload elsewhere.

Horizontal scaling

No concept of “I want 10 of these, and 40 at peak.” You scale by running more commands on more machines, by hand.

Service discovery & load balancing

Container IPs change on every restart. Docker gives you no stable virtual IP or DNS name in front of a changing set of replicas.

Zero-downtime rollouts

No built-in way to replace v1 with v2 gradually, verify health, and roll back automatically on failure.

Declarative desired state

Docker commands are imperative: do this now. Nothing keeps watching to make sure it stayed true five minutes later.

Config & secrets at scale

Env vars and bind mounts per host do not scale to many apps, environments, and rotating credentials.

Storage orchestration

A volume is local to one machine. If a container moves, its data does not follow it.

The one-sentence answer

Docker makes a container runnable. Kubernetes makes a set of containers reliable — by continuously comparing declared state to observed state and acting to close the gap.

When Kubernetes is the right answer

Microservices

Many small services that need to find each other, be versioned independently, and scale at different rates.

Frequent releases

Several deploys a day with rolling updates, health gates, and a one-command rollback.

Bursty traffic

Demand that varies by hour or season, where paying for peak capacity all month is wasteful.

High availability

Workloads that must survive a node, rack, or zone failure without a human on call.

Hybrid & multi-cloud

One API and one set of manifests across AWS, Azure, GCP, and on-prem hardware.

Batch & ML jobs

Job and CronJob objects that bin-pack onto spare capacity, including GPU nodes.

When it is the wrong answer

A single small app with steady traffic, a team of two, and no HA requirement does not need a cluster. Kubernetes is complexity you adopt to buy back reliability and speed — if you are not spending the reliability budget, you are just paying the complexity cost. A managed PaaS or a single VM with Compose is often correct.

Kubernetes vs Docker Compose

Compose is the closest comparison, because it is also declarative and also describes a multi-container app. The difference is the blast radius it can survive.

A useful mental model: Compose describes an app. Kubernetes describes a system that keeps an app running. Many teams use Compose locally and Kubernetes in production, from the same images.

A real-world example

An online store: web (frontend), catalog, cart, payments, plus Redis and Postgres. Normal load is 3 web replicas. A sale starts at 9am.

With Docker alone

  • SSH into each server, docker run more web containers.
  • Hand-edit the load balancer config with the new IPs and ports.
  • At 09:14 a node runs out of memory; two containers die. Nobody notices until checkout errors spike.
  • A payments hotfix means stop-and-start — a visible outage window.
  • After the sale, SSH back in and tear the extra containers down by hand.

With Kubernetes

  • An HPA sees CPU pass its target and scales web from 3 to 24 replicas.
  • The scheduler places them on nodes with free capacity; the cluster autoscaler adds nodes if there is none.
  • New pods join the Service’s endpoint list automatically — only once their readiness probe passes.
  • The OOM-killed pods restart immediately; traffic was removed from them the moment they went unready.
  • The payments hotfix rolls out pod by pod, with zero downtime and kubectl rollout undo standing by.
  • At 11pm traffic drops and the HPA scales back down. Nobody was paged.
Recall check

Name three things that fail with Docker alone but are handled automatically in Kubernetes. — Rescheduling after node failure, load-balanced service discovery over changing pod IPs, and health-gated rolling updates with rollback.

02

Kubernetes architecture

A cluster is one brain (the control plane) driving many muscles (worker nodes). The brain never runs your app; it only decides and records. The nodes never decide; they only execute and report back.

The cluster

A cluster is a set of machines — physical or virtual — presented to you as a single pool of CPU, memory, and storage. You stop addressing machines by name and start declaring workloads. Which machine ends up running your container becomes an implementation detail that Kubernetes manages.

Control plane and worker nodes

Control plane

Holds the cluster’s desired state and runs the loops that pursue it. In production it is replicated across 3 or 5 machines so that losing one does not lose the cluster. Managed services (EKS, GKE, AKS) run it for you and you never see those machines.

If it goes down: running pods keep serving traffic, but nothing new can be created, scaled, healed, or changed. The cluster freezes in place.

Worker nodes

Where your containers actually run. Each node needs three things: kubelet (the agent), kube-proxy (the traffic rules), and a container runtime. Nodes are cattle — adding or removing one should be uneventful.

If one goes down: the control plane notices the missing heartbeat and recreates its pods elsewhere.

How the pieces communicate

The architecture has one rule that explains almost every behaviour you will see:

The hub-and-spoke rule

The API server is the only component that talks to etcd, and every other component talks only to the API server. Nothing calls anything else directly.

Components do not poll on a timer — they open a long-lived watch on the API server and receive a stream of change events. The scheduler watches for unscheduled pods. Each controller watches the objects it owns. Each kubelet watches for pods assigned to its own node. This is why the system is loosely coupled: you can restart the scheduler and nothing else notices.

Communication is secured with TLS and mutual authentication; every request is authenticated, authorised through RBAC, and passed through admission controllers before anything is written.

03

Components, one by one

For each component, the useful thing to hold in your head is: what does it watch, what does it write, and what breaks if it stops?

Control plane components

kube-apiserver — the front door

A REST server over the cluster’s object model, and the only component with write access to etcd. Every kubectl command, every controller, every kubelet, and every dashboard goes through it.

Every incoming request passes four gates:

  1. Authentication — who are you? (client certs, bearer tokens, service account tokens, OIDC)
  2. Authorisation — are you allowed to do this verb on this resource in this namespace? (RBAC)
  3. Admission control — mutating webhooks can rewrite the object (inject a sidecar, add defaults); validating webhooks can reject it (policy, quotas).
  4. Validation & persistence — the object is schema-checked and written to etcd.

It is horizontally scalable and stateless — run several behind a load balancer.

If it stops: the cluster becomes read-only in practice. Existing pods keep running, but no changes, no healing, no scaling, and kubectl fails.

etcd — the cluster’s memory

A distributed, strongly consistent key-value store using the Raft consensus algorithm. It holds all cluster state: every object spec, status, ConfigMap, and Secret. Delete etcd and you have deleted the cluster.

  • Run an odd number of members (3 or 5) so a majority quorum can always be formed. 3 members tolerate 1 failure; 5 tolerate 2.
  • Its watch API is what makes the whole event-driven architecture possible.
  • It is latency-sensitive — give it fast disks; slow etcd shows up as a slow cluster everywhere.
  • Back it up. An etcd snapshot is your disaster-recovery plan: etcdctl snapshot save.

If it stops: the API server has nothing to read or write. The cluster stops accepting changes; loss of quorum without a backup is unrecoverable.

kube-scheduler — placement only

Watches for pods with no nodeName set, picks a node for each, and writes that choice back to the API server. That write is the entire job — the scheduler never contacts a node and never starts a container.

It decides in two phases:

  • Filtering — eliminate nodes that cannot work: not enough free CPU/memory for the pod’s requests, missing node selector labels, an untolerated taint, a port conflict, an unavailable volume.
  • Scoring — rank the survivors: spread across nodes and zones, image already cached locally, affinity and anti-affinity preferences, least-loaded first. Highest score wins; ties are broken randomly.

Your levers: nodeSelector, nodeAffinity, podAffinity / podAntiAffinity, taints and tolerations, topologySpreadConstraints, and priorityClassName (which can evict lower-priority pods to make room).

If it stops: new pods sit in Pending forever. Existing pods are untouched.

kube-controller-manager — the reconciliation loops

One binary running dozens of independent controllers, each an infinite loop of: observe actual state → compare to desired state → take one step to close the gap. This is the pattern the whole system is built on.

  • Deployment controller — creates and steps ReplicaSets to perform rollouts.
  • ReplicaSet controller — keeps exactly N pods matching a label selector.
  • Node controller — watches node heartbeats; marks a silent node NotReady and, after a grace period (~5 minutes by default via taint-based eviction), evicts its pods so they can be rescheduled.
  • Job / CronJob controllers — run pods to completion, on a schedule.
  • Endpoints / EndpointSlice controller — keeps each Service’s list of ready pod IPs current.
  • ServiceAccount, PV binder, namespace, TTL controllers, and many more.

If it stops: nothing self-heals. Crashed pods are not replaced, rollouts stall, and Service endpoints go stale.

cloud-controller-manager — the cloud adapter

Split out of the controller manager so that cloud-specific code lives behind a stable interface. It only exists on managed or cloud-hosted clusters.

  • Node controller — asks the cloud API whether a missing VM was actually deleted, and labels nodes with region/zone/instance type.
  • Service controller — provisions a real cloud load balancer when you create a type: LoadBalancer Service, and writes its address back into the object.
  • Route controller — configures the VPC routes that let pod networks reach each other.

If it stops: LoadBalancer Services stay <pending> and deleted VMs linger as ghost nodes. On bare metal it is simply absent.

Worker node components

kubelet — the node’s agent

The one component that actually makes containers exist. It watches the API server for pods bound to its node and drives the local runtime until reality matches the spec.

Its responsibilities:

  • Pull images, create the pod sandbox and its containers through the CRI.
  • Mount volumes, inject ConfigMaps, Secrets, and the service account token.
  • Run liveness, readiness, and startup probes, and act on the results.
  • Report pod status and node conditions (memory pressure, disk pressure) back to the API server as a heartbeat.
  • Evict pods when the node runs low on memory or disk.

It only manages pods Kubernetes knows about — plus static pods defined by files on disk, which is how control plane components are themselves bootstrapped with kubeadm.

If it stops: containers on that node keep running, but nothing on the node can change, and the missing heartbeat makes the control plane mark the node NotReady and move its workloads.

kube-proxy — the traffic rules

Implements the Service abstraction on every node. It watches Services and EndpointSlices and programs kernel rules so that traffic to a Service’s virtual IP is rewritten to a real pod IP.

  • iptables mode (common default) — installs NAT rules; selection is effectively random per connection. Rule count grows with the number of services.
  • IPVS mode — uses the kernel’s load balancer with hash tables; scales to thousands of services and offers real algorithms (round-robin, least-conn).
  • Increasingly replaced by eBPF datapaths (for example Cilium’s kube-proxy replacement).

Key point: it is not a proxy sitting in the data path for most traffic — it is a rule writer. Packets are rewritten by the kernel, not passed through a userspace process.

If it stops: pod-to-pod traffic by IP still works, but Service virtual IPs on that node stop resolving to backends.

Container runtime — the thing that runs containers

The kubelet does not create containers itself; it calls a runtime over the Container Runtime Interface (CRI), a gRPC API. Any runtime that implements CRI works: containerd (most common), CRI-O, or others.

Below CRI sits a low-level OCI runtime — usually runc — which makes the actual namespaces and cgroups. Sandboxed runtimes like gVisor or Kata Containers can be swapped in for stronger isolation via a RuntimeClass.

The Docker connection: Kubernetes removed dockershim in v1.24, so the Docker daemon is no longer a supported runtime. Images built by Docker still run perfectly, because they follow the OCI image spec — and containerd was already doing the real work inside Docker anyway.

Recall check

A pod is stuck in Pending. Which component is involved, and what are the three usual causes? — The scheduler: no node has enough free CPU/memory for the pod’s requests, no node matches its selector/affinity, or an untolerated taint (and separately: an unbound PVC).

04

The core objects

Almost every object shares the same four top-level fields: apiVersion, kind, metadata, and spec — plus a status that Kubernetes writes for you. You declare spec; the controllers work to make status match it.

Labels are the glue

Objects are not wired together by name or by pointer. A Service finds pods, and a ReplicaSet owns pods, through a label selector — a query over labels. Get a selector wrong and you get a Service with no endpoints, or a ReplicaSet fighting another for the same pods.

Pod

The smallest deployable unit — not a container. A pod is one or more containers that share a network namespace (the same IP and port space, so they reach each other over localhost), share volumes, and are always scheduled together onto one node. Most pods hold exactly one application container.

  • Sidecar pattern: a second container in the pod — a log shipper, a proxy, a metrics exporter.
  • Init containers run to completion, in order, before the app containers start — for migrations or waiting on a dependency.
  • Pods are mortal and disposable. They are never repaired, only replaced, and the replacement gets a new name and a new IP.
apiVersion: v1
kind: Pod
metadata:
  name: web
  labels:
    app: web          # how Services and ReplicaSets will find this pod
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80
      resources:
        requests: { cpu: "100m", memory: "128Mi" }
        limits:   { cpu: "500m", memory: "256Mi" }
Never create bare pods in production

A pod created directly has nothing watching it. If its node dies, it is gone permanently. Always let a controller (Deployment, StatefulSet, DaemonSet, Job) own your pods.

ReplicaSet

One job: keep exactly replicas pods matching its selector alive. Too few → create more from the pod template. Too many → delete some. That is the self-healing you saw at the top of this page.

You rarely write one by hand. You write a Deployment, and it manages ReplicaSets for you — because a ReplicaSet alone cannot update pods to a new image gracefully.

Deployment

The object you will use most for stateless apps. It owns ReplicaSets, and uses them to perform versioned, gradual rollouts with history and rollback.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }     # must match template.metadata.labels
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                 # 1 extra pod allowed above replicas
      maxUnavailable: 0           # never drop below 3 ready pods
  template:                       # <- this is a Pod template
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: myrepo/web:2.4.1
          ports: [ { containerPort: 8080 } ]
          readinessProbe:
            httpGet: { path: /healthz, port: 8080 }
            initialDelaySeconds: 5

Changing the image field creates a new ReplicaSet and scales it up while scaling the old one down. The old ReplicaSet is kept at 0 replicas so that kubectl rollout undo can scale it straight back up.

Service

A stable network identity in front of a changing set of pods. Pods come and go with new IPs; the Service’s ClusterIP and DNS name never change. It also load balances across the healthy backends.

apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  type: ClusterIP
  selector:
    app: web        # every ready pod with this label becomes an endpoint
  ports:
    - port: 80        # the Service port
      targetPort: 8080  # the container port

Only pods that pass their readiness probe are added to the endpoint list. That is the mechanism behind zero-downtime rollouts.

Namespace

A virtual cluster inside the cluster: a scope for names, and a boundary for quotas, RBAC, and network policy. Two teams can each have a web Deployment without colliding.

  • Names must be unique within a namespace, not across the cluster.
  • Cross-namespace DNS is explicit: web.payments.svc.cluster.local.
  • Not everything is namespaced — Nodes, PersistentVolumes, StorageClasses, and ClusterRoles are cluster-scoped.
  • Built-ins: default, kube-system, kube-public, kube-node-lease.
A namespace is not a security boundary by itself

By default any pod can reach any other pod in any namespace over the network. You get isolation only when you add RBAC, ResourceQuotas, and NetworkPolicies on top.

ConfigMap

Non-secret configuration kept outside the image, so the same image can run in dev, staging, and production. Consume it as environment variables or as files mounted into the container.

apiVersion: v1
kind: ConfigMap
metadata:
  name: web-config
data:
  LOG_LEVEL: "info"
  FEATURE_CHECKOUT_V2: "true"
  app.properties: |
    timeout=30s
    retries=3
---
# consumed in a pod spec:
envFrom:
  - configMapRef: { name: web-config }
# or mounted as files:
volumes:
  - name: cfg
    configMap: { name: web-config }

Secret

Same shape as a ConfigMap, for sensitive values: passwords, tokens, TLS keys, registry credentials. Kubernetes treats them more carefully — they are not written to node disk in plain text, and they can be restricted with RBAC.

base64 is encoding, not encryption

Anyone who can read the Secret object can trivially decode it. To actually protect secrets you need: encryption at rest for etcd, tight RBAC on the secrets resource, and ideally an external store (External Secrets Operator, Vault, or a cloud secrets manager with CSI). Never commit a Secret manifest to git — use Sealed Secrets or SOPS if you must.

Volume, PersistentVolume, PersistentVolumeClaim

A container’s filesystem dies with the container. Volumes fix that at three different lifespans:

Volume

Lives as long as the pod. emptyDir is scratch space shared between containers in the pod; it is deleted when the pod is removed.

PersistentVolume

A piece of real storage in the cluster (EBS disk, NFS export, Ceph RBD). Cluster-scoped, with a lifecycle independent of any pod.

PersistentVolumeClaim

A pod’s request for storage: “20Gi, ReadWriteOnce, fast class.” Kubernetes binds it to a matching PV, or provisions one on demand.

The split matters: your app manifest asks for a claim and never mentions EBS or NFS, so it stays portable. Details are in section 8.

05

How Kubernetes actually runs an application

Two directions are happening at once, and separating them is what makes the whole picture click: ownership flows downward from your manifest to a container, and traffic flows inward from the user to that container.

One correction to the classic arrow chain

The often-drawn chain Pod → Deployment → ReplicaSet is the order you learn the concepts, not the order things are created. In reality the Deployment comes first: it creates a ReplicaSet, and the ReplicaSet creates the Pods. Ownership points downward, and you can see it in metadata.ownerReferences.

The full path, end to end

  1. Build and push. docker build -t myrepo/web:2.4.1 . then push to a registry. Use an immutable tag or a digest — never :latest in production.
  2. Declare. Write the Deployment manifest referencing that image, plus a Service and an Ingress.
  3. Apply. kubectl apply -f k8s/ sends the objects to the API server, which validates and stores them in etcd.
  4. Reconcile. The Deployment controller creates a ReplicaSet; the ReplicaSet controller creates 3 pods, which have no node yet.
  5. Schedule. The scheduler filters and scores nodes, then writes nodeName onto each pod.
  6. Start. Each kubelet sees a pod for its node, pulls the image through the CRI, mounts volumes and secrets, and starts the containers.
  7. Become ready. The readiness probe passes; the endpoint controller adds the pod IP to the Service’s EndpointSlice.
  8. Program the datapath. kube-proxy on every node updates its rules so the Service’s ClusterIP now has three backends.
  9. Serve. A user hits the DNS name → cloud load balancer → ingress controller pod → matched by host/path rule → Service → one pod IP → your container.
Recall check

You changed one line in a Deployment’s image tag. How many new objects appear? — One new ReplicaSet (the old one stays at 0 for rollback) plus new pods; the Deployment, Service, and Ingress are updated or untouched, not replaced.

06

Networking

Kubernetes networking rests on one promise: every pod gets its own IP, and every pod can reach every other pod directly, on any node, without NAT. Once you accept that flat network, everything else is a convenience built on top.

Pod IPs and the flat network

Each pod gets a unique cluster-internal IP. Containers inside a pod share that IP and talk over localhost — which is why two containers in the same pod cannot both bind port 8080.

Kubernetes does not implement this network itself. It defines the contract and delegates to a CNI plugin — Calico, Cilium, Flannel, or a cloud-native one like AWS VPC CNI — which assigns addresses and sets up the routing.

Pod IPs are worthless to hold on to

Restart a pod and its IP changes. Never write a pod IP into config, never cache one. That instability is precisely the problem Services exist to hide.

Service IPs

A Service gets a ClusterIP from a separate virtual range. Nothing answers on that IP — no process, no interface. It is a fiction maintained by kernel rules that kube-proxy writes on every node: packets to the ClusterIP are rewritten to one of the ready pod IPs. The Service’s IP and DNS name are stable for its whole life, no matter how many times the pods behind it are replaced.

The four ways to expose an app

These are cumulative, not alternatives — NodePort contains a ClusterIP, LoadBalancer contains a NodePort, and Ingress sits in front of Services.

Internal only, and the default. Reachable from inside the cluster at a virtual IP and a DNS name. This is what you want for every service that only other services call — databases, internal APIs, caches.

spec:
  type: ClusterIP          # default, can be omitted
  selector: { app: web }
  ports: [ { port: 80, targetPort: 8080 } ]

Opens the same port on every node. Traffic to anyNodeIP:30080 is forwarded to the Service and then to a pod — even if that node runs none of the pods. Useful for on-prem clusters and quick demos; clumsy for real traffic because of the high port range (30000–32767) and because clients must know node IPs.

spec:
  type: NodePort
  selector: { app: web }
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080      # optional; auto-assigned from 30000-32767

Asks the cloud for a real load balancer. The cloud controller provisions one, points it at the NodePorts, and writes its public IP or hostname into the Service’s status. Simple and production-grade — but it is one external load balancer, with its own bill, per Service.

spec:
  type: LoadBalancer
  selector: { app: web }
  ports: [ { port: 443, targetPort: 8080 } ]
# kubectl get svc web  ->  EXTERNAL-IP appears once provisioned

One entry point, many services. Ingress is an HTTP/HTTPS router: rules match on host and path and forward to different Services. It needs an ingress controller (NGINX, Traefik, HAProxy, or a cloud one) actually running in the cluster — the Ingress object alone does nothing. Typically the controller itself sits behind a single LoadBalancer Service, so you pay for one load balancer instead of twenty.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
spec:
  ingressClassName: nginx
  tls:
    - hosts: [ shop.example.com ]
      secretName: shop-tls
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: { name: api, port: { number: 80 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: storefront, port: { number: 80 } }
Two more Service shapes worth knowing

Headless (clusterIP: None): no virtual IP and no load balancing — DNS returns the individual pod IPs instead. This is how StatefulSets give each replica an addressable name. ExternalName: no proxying at all, just a DNS CNAME to an outside host, useful for pointing at a managed database.

For anything beyond HTTP routing — gRPC, TCP, traffic splitting, cross-namespace delegation — the newer Gateway API is the direction the ecosystem is heading.

DNS inside the cluster

CoreDNS runs as a Deployment in kube-system and every pod is configured to use it. Each Service gets a predictable record:

<service>.<namespace>.svc.cluster.local

web                      # same namespace  (short form works)
web.payments             # another namespace
web.payments.svc.cluster.local    # fully qualified

# headless services resolve to individual pods:
web-0.web.payments.svc.cluster.local

This is what makes service discovery boring: application code connects to http://payments and never learns an IP.

Pod-to-pod communication, step by step

  1. Pod A resolves payments through CoreDNS and gets the Service’s ClusterIP.
  2. It sends a packet to that virtual IP.
  3. Kernel rules written by kube-proxy on Pod A’s node rewrite the destination to one ready pod IP — chosen at connection time.
  4. The CNI routes the packet to that pod, on whatever node it happens to be.
  5. The reply returns along the same translated path; Pod A believes it spoke to the ClusterIP the whole time.

Same-node and cross-node traffic behave identically from the application’s point of view. That uniformity is the value of the flat network model.

Recall check

kubectl get endpoints web returns none. What are the likely causes? — The Service selector does not match the pod labels, the pods are not passing readiness, or targetPort does not match the port the container actually listens on.

Scaling and self-healing

This is where the control loop pays for itself. Every behaviour below is the same pattern — a controller comparing desired to actual, and taking one corrective step — applied to a different kind of failure.

Replicas

Setting replicas: 5 means “five ready copies exist at all times,” not “start five copies.” That distinction is the entire difference from docker run. Scale by hand with kubectl scale deploy/web --replicas=10, or better, by editing the manifest so git stays the source of truth.

Replicas buy you two things at once: capacity, and survival of individual failures. With one replica, any restart is an outage.

Horizontal Pod Autoscaler

An HPA watches a metric and rewrites the replica count on your behalf. It requires metrics-server to be installed, and it requires your pods to declare resource requests — utilisation is a percentage of the request, so without one there is nothing to compute.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: web }
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 50 }
Try the HPA formula
50%
target 50% · current 4 replicas · min 2 · max 20

Two details that keep this from thrashing: a 10% tolerance band means small deviations are ignored, and a stabilisation window (5 minutes by default for scale-down) stops the count oscillating. Scale-up is deliberately fast, scale-down deliberately slow.

Three autoscalers, three jobs

HPA adds more pods. VPA changes an existing pod’s CPU/memory requests (and until in-place resize matures, that means restarting it). Cluster Autoscaler adds and removes nodes when pods cannot be scheduled or nodes sit empty. HPA and VPA on the same CPU metric will fight; do not do it.

Restarting failed containers

The kubelet handles this locally, guided by the pod’s restartPolicy (Always for Deployments, OnFailure or Never for Jobs). A container is restarted when its process exits non-zero, when it is OOM-killed, or when its liveness probe fails.

Restarts back off exponentially — 10s, 20s, 40s, up to 5 minutes — which is the state you see as CrashLoopBackOff. That is not an error in itself; it is Kubernetes saying “this keeps dying, so I am waiting longer between attempts.” Read the logs of the dead instance with kubectl logs pod --previous.

Rescheduling failed pods

Node-level failure is handled by the control plane, not the kubelet (which is gone along with its node). The sequence:

  1. The kubelet stops sending heartbeats (node lease updates).
  2. After ~40 seconds the node controller marks the node NotReady.
  3. Taints are applied, and after a toleration period of about 5 minutes the pods on that node are marked for eviction.
  4. Their owning ReplicaSet sees fewer pods than desired and creates replacements.
  5. The scheduler places the replacements on healthy nodes, and they get new names and new IPs.

Pods are also evicted before total failure, when a node reports memory or disk pressure — lowest-priority and most over-consuming pods go first.

Spreading matters

Three replicas that the scheduler happened to place on one node give you no protection from node failure. Use topologySpreadConstraints or pod anti-affinity to force replicas across nodes and zones, and a PodDisruptionBudget to stop voluntary operations (like a node drain during an upgrade) from taking too many down at once.

Rolling updates

Changing the pod template triggers a rollout. The Deployment controller creates a new ReplicaSet and shifts replicas from old to new, a few at a time, governed by two knobs:

  • maxUnavailable — how far below the desired count you will dip. Set 0 to never lose capacity.
  • maxSurge — how many extra pods above the desired count are allowed temporarily. Needs spare cluster capacity.

Critically, a new pod only counts as available once its readiness probe passes. Without probes, Kubernetes assumes a started container is ready and will happily roll a broken version all the way out.

Watch a rolling updatereplicas 4 · maxSurge 1 · maxUnavailable 0
Steady at v1. 4 of 4 ready.

Rollbacks

Because the old ReplicaSet is kept at zero replicas rather than deleted, reverting is just scaling it back up — which is fast and needs no rebuild, no registry pull, and no pipeline run.

kubectl rollout status deploy/webBlock until the rollout finishes or fails
kubectl rollout history deploy/webList revisions
kubectl rollout undo deploy/webBack to the previous revision
kubectl rollout undo deploy/web --to-revision=3Back to a specific revision
kubectl rollout pause deploy/webFreeze mid-rollout to inspect a canary
kubectl rollout restart deploy/webRecreate all pods — e.g. to pick up a changed Secret

Keep in mind what a rollback does not undo: database migrations, and anything already consumed by another system. Application-level compatibility is still your problem. Also note that revisionHistoryLimit (default 10) caps how far back you can go, and rollbacks revert the pod template only — not replica count or other spec changes.

Recall check

With maxSurge: 0 and maxUnavailable: 0, what happens on a rollout? — Nothing. The rollout cannot make progress, because it is allowed neither an extra pod nor a missing one. At least one must be non-zero.

Configuration and storage

Containers are immutable and disposable. Anything that must differ between environments, or survive a restart, has to live outside the image — that is what this whole section is about.

ConfigMaps in practice

Two ways to consume one, with an important difference:

As environment variables

Simple, and what most twelve-factor apps expect. But env vars are read once at process start — changing the ConfigMap does not update a running pod. You must restart it.

As mounted files

Each key becomes a file. The kubelet does refresh mounted contents (within a minute or so), so an app that watches its config file can reload without a restart.

A common trick: put a hash of the ConfigMap into a pod-template annotation, so that changing the config changes the template and automatically triggers a rolling update. Helm charts do this routinely.

Secrets in practice

  • Mount them as files rather than env vars where you can — env vars leak into crash dumps, logs, and kubectl describe output of child processes.
  • Turn on encryption at rest for etcd, or Secrets are stored effectively in the clear.
  • Lock down the secrets resource in RBAC. A user who can read secrets in a namespace can read all of them.
  • Special types matter: kubernetes.io/tls for Ingress certificates, kubernetes.io/dockerconfigjson for private registry pulls.
  • For real credential lifecycle — rotation, audit, short-lived tokens — use an external manager (Vault, cloud secret stores) via the Secrets Store CSI driver or External Secrets Operator.

Volumes

A volume is declared on the pod and mounted into one or more of its containers. Its lifetime is the pod’s, not the container’s — so a container can crash and restart with its volume data intact.

TypeLives as long asUse it for
emptyDirThe podScratch space, caches, sharing files between containers in one pod
configMap / secretThe podInjecting configuration and credentials as files
hostPathThe nodeNode agents that need host files. Avoid otherwise — it breaks portability and is a security risk
persistentVolumeClaimIndependent of the podReal data that must survive rescheduling
projected / downwardAPIThe podService account tokens, pod metadata exposed as files

PersistentVolumes, Claims, and StorageClasses

The three-part split exists so that application authors never have to know what storage the cluster actually has.

Static vs dynamic: an admin can pre-create PVs and let claims match them, but almost everyone uses dynamic provisioning — the PVC names a StorageClass, and a CSI driver creates real storage and its PV automatically.

Access modes

  • ReadWriteOnce (RWO) — mounted read-write by pods on a single node. Block storage like EBS. The common case.
  • ReadOnlyMany (ROX) — many nodes, read only.
  • ReadWriteMany (RWX) — many nodes, read-write. Needs a shared filesystem (NFS, CephFS, EFS); most block storage cannot do it.

Reclaim policy

Delete destroys the underlying storage when the claim goes away — convenient, and dangerous for databases. Retain keeps the data and leaves the PV in Released for an admin to handle. Choose deliberately, per StorageClass.

An RWO volume pins a pod to a node

A pod using an RWO volume can only be scheduled where that volume can attach — often one specific availability zone. This is a frequent cause of a pod stuck in Pending after a node failure, and a reason to use WaitForFirstConsumer volume binding so the disk is created in the zone the pod actually lands in.

Stateful workloads

Deployments treat pods as interchangeable, which is exactly wrong for a database replica set. StatefulSet changes four things:

  • Stable identity — pods are named db-0, db-1, db-2 and keep those names across restarts.
  • Stable storage — each pod gets its own PVC from a volumeClaimTemplate, and reattaches to the same volume when it restarts.
  • Ordered operations — created and scaled up in order, terminated and rolled in reverse order.
  • Stable DNS — paired with a headless Service, each pod is individually addressable at db-0.db.ns.svc.cluster.local.
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: db }
spec:
  serviceName: db            # the headless Service
  replicas: 3
  selector: { matchLabels: { app: db } }
  template:
    metadata: { labels: { app: db } }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          volumeMounts:
            - { name: data, mountPath: /var/lib/postgresql/data }
  volumeClaimTemplates:      # one PVC per pod, kept on delete
    - metadata: { name: data }
      spec:
        accessModes: [ ReadWriteOnce ]
        storageClassName: fast
        resources: { requests: { storage: 20Gi } }

A StatefulSet gives you identity and storage. It does not give you replication, failover, or backups — those are the database’s job. For production data, seriously consider a managed database or a purpose-built operator instead of rolling your own.

Recall check

Why can’t you just add a PVC to a Deployment with 3 replicas? — All three pods would share the one claim. With RWO that means two stay Pending; with RWX it means three processes writing the same files. Use a StatefulSet so each replica gets its own volume.

Kubernetes in production

A cluster that works on your laptop and a cluster you can be paged for differ by exactly this list. Most production incidents trace back to a missing probe, a missing resource request, or a missing limit.

Health checks

Kubernetes cannot tell a hung process from a busy one unless you tell it how to ask. Three probes, three different questions:

ProbeQuestionOn failureTypical check
livenessIs this process still healthy?Kill and restart the containerA cheap endpoint that proves the event loop is alive
readinessCan it take traffic right now?Remove the pod from Service endpoints (no restart)Dependencies checked: DB reachable, cache warm
startupHas it finished booting?Kill it if boot exceeds the budget; suppresses the other two until it passesSame as liveness, with a generous failureThreshold
 
startupProbe:                     # slow starters: up to 30 x 10s = 5 min to boot
  httpGet: { path: /healthz, port: 8080 }
  failureThreshold: 30
  periodSeconds: 10
readinessProbe:                   # gates traffic
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
livenessProbe:                    # gates restarts - keep it simple
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3
The classic outage

Pointing a liveness probe at an endpoint that checks the database. The database has a slow minute; every replica’s liveness fails at once; Kubernetes restarts them all; the outage is now total and self-inflicted. Liveness = am I alive. Readiness = can I serve. Dependencies belong only in readiness.

Resource requests and limits

Requests are what the scheduler reserves for you — they determine placement and are the denominator for HPA utilisation. Limits are the hard ceiling the kernel enforces. Exceed a CPU limit and you are throttled; exceed a memory limit and the container is OOM-killed.

  • Always set memory requests and limits, equal to each other for predictable workloads. Memory is incompressible — there is no throttling, only killing.
  • Set CPU requests. Be careful with CPU limits — aggressive limits cause latency from throttling even when the node is idle. Many teams deliberately omit them.
  • QoS classes decide who dies first under node pressure: Guaranteed (requests == limits for every container) → Burstable (requests set, lower than limits) → BestEffort (nothing set, evicted first).

Namespaces as guardrails

Beyond naming, namespaces are where you attach limits: a ResourceQuota caps total CPU, memory, and object counts for a team; a LimitRange supplies default requests and limits so that a pod submitted without them does not land unbounded. Common layouts are per-environment (dev, staging, prod) or per-team, though separate clusters are the stronger boundary for prod.

RBAC

Four objects, and the model is simple once you see the pairs: a Role is a set of allowed verbs on resources in one namespace; a ClusterRole is the same but cluster-wide; a RoleBinding grants a Role (or ClusterRole) to subjects in one namespace; a ClusterRoleBinding grants it everywhere.

kind: Role
metadata: { namespace: payments, name: pod-reader }
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]
---
kind: RoleBinding
metadata: { namespace: payments, name: devs-read-pods }
subjects:
  - { kind: Group, name: payments-devs, apiGroup: rbac.authorization.k8s.io }
roleRef:
  { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }
  • Permissions are additive only — there is no deny rule. You grant, you never revoke by rule.
  • Workloads authenticate as a ServiceAccount. Give each app its own, with the narrowest role it needs, and disable token automounting where it is not used.
  • Check your work: kubectl auth can-i delete pods --as=alice -n payments.

Security

NetworkPolicy

The default is wide open: any pod can talk to any pod. A NetworkPolicy selects pods and restricts their ingress and egress. Start with a default-deny in each namespace, then allow what is needed. Requires a CNI that supports it.

Pod Security Admission

Enforces the baseline or restricted standard per namespace via labels. Blocks privileged containers, host namespaces, and host paths — the replacement for PodSecurityPolicy.

Harden the container

runAsNonRoot, a read-only root filesystem, dropped capabilities, no privilege escalation. Small base images mean fewer CVEs to patch.

Supply chain

Scan images in CI, pin by digest, sign and verify, and use admission policy (Kyverno, OPA Gatekeeper) to reject anything unsigned or from an untrusted registry.

Logging

The contract is: write logs to stdout and stderr, unstructured file paths are not your problem. The kubelet captures those streams to files on the node, and a DaemonSet agent (Fluent Bit, Vector, Promtail) ships them to a backend such as Elasticsearch, Loki, or a managed service.

Node-local logs are rotated and lost when the pod is deleted — kubectl logs is for debugging right now, never for retention. Log in JSON with a request ID, and always include the pod, namespace, and container labels.

Monitoring

  • metrics-server — lightweight, powers kubectl top and the HPA. Not a monitoring system; it keeps no history.
  • Prometheus — scrapes /metrics endpoints, stores time series, evaluates alerting rules. Usually installed with Grafana and Alertmanager via the kube-prometheus-stack chart.
  • kube-state-metrics — exposes object state (desired vs ready replicas, pod restarts, job failures) rather than resource usage. This is where you catch a Deployment that has silently been degraded for a week.
  • What to alert on: the golden signals (latency, traffic, errors, saturation) at the service level, plus cluster-level symptoms — pods crash-looping, nodes NotReady, PVCs near full, certificates expiring, HPA pinned at max.
  • Tracing (OpenTelemetry) matters more here than in a monolith: one user request now crosses several pods.

Helm

Raw YAML does not survive multiple environments — you end up copying near-identical files and editing image tags by hand. Helm packages a set of templated manifests as a chart, with a values.yaml supplying the variables, and tracks each install as a versioned release that can be upgraded and rolled back.

helm install web ./chart -f values.prod.yamlCreate a release
helm upgrade --install web ./chart --atomicIdempotent deploy; roll back automatically on failure
helm template web ./chart | kubectl diff -f -See the rendered change before applying it
helm rollback web 3Return to a previous release

Kustomize is the common alternative: no templating language, just a base plus per-environment overlay patches, and it is built into kubectl apply -k. Helm suits distributing software to others; Kustomize suits your own apps across environments.

CI/CD

A typical pipeline: commit → test → build image → scan → push with an immutable tag → update the manifest → apply → watch kubectl rollout status and fail the build if it does not converge.

GitOps inverts the last step. Instead of the pipeline pushing to the cluster with admin credentials, an in-cluster agent (Argo CD, Flux) pulls from git and continuously reconciles the cluster to match — the same control-loop idea applied to deployment. You get an audit trail, drift detection, and rollback by git revert.

Never deploy :latest

With a mutable tag, Kubernetes cannot tell that anything changed, so no rollout happens — and any pod that restarts may silently pull a different build than its siblings. Use the commit SHA as the tag, or pin the digest.

A pre-production checklist

  • Readiness and liveness probes on every container, with liveness free of external dependencies.
  • Resource requests everywhere; memory limits everywhere; CPU limits considered, not reflexive.
  • More than one replica, spread across nodes and zones, with a PodDisruptionBudget.
  • terminationGracePeriodSeconds long enough for in-flight requests, and a preStop sleep so endpoints are withdrawn before the process exits.
  • Rollout strategy tuned, plus a rehearsed rollback.
  • Secrets out of git and out of images; encryption at rest on.
  • NetworkPolicies, a restricted pod security level, and a non-root container.
  • Dashboards and alerts that would wake someone before users notice.
  • etcd backups — tested by restoring them.
